# Demo examples

Three examples, with the **real output of the running backend** (`POST /predict`
against `apps/backend`, served from `data/applications.parquet`, 10,005 rows).

**Revision note:** an earlier version of this file used a standalone matching
script (`pick_demo_examples.py`) to pick numbers before the backend existed.
Once the backend was built, its matcher turned out to use proper progressive
band-widening (`apps/backend/.../services/matching.py`, bands of (±30%/±2
storeys) → (±50%/±3) → (±50%/any storeys) → (±100%/any storeys), stopping once
`min_similar=20` is hit) — a better algorithm than the fixed single band this
file was first built from, and the two don't agree on `n_similar` or the rates.
**The backend is correct; this file is now generated from its actual output,**
so what's written here is exactly what the live demo will show.

**How to reproduce this file:** run the backend (`uvicorn planning_predictor.main:app`
from `apps/backend`, with `data/applications.parquet` present) and `POST` the
three "Type this live" inputs below to `/predict`. Re-run before rehearsing if
`applications.parquet` has been regenerated since.

## Data gaps that still apply regardless of which matcher is used

- **Dublin City Council and Dún Laoghaire–Rathdown have 0% link fill** (`link` is `null` for every row — 1,246 and 304 rows respectively). Don't use either for the live "click through to a real application" demo moment.
- **Cork City and Cork County show exactly 0% further-information requests** (and Cork County 0% appeals too) at a volume where that isn't plausible — reads as those two authorities not populating `FIRequestDate`/`AppealSubmittedDate` in this register, not a real finding. Avoid them for the delay-factor demo moment.

Both are detailed in `data/schema.md`.
